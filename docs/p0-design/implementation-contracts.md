Requirement sources are the CUS/SR/task entries in the current registry and the project brief. Interface proposals are cross-checked against `docs/management/wp01-requirements-package.md`.

## Cross-cutting contract rules

1. Every persisted object and every request is scoped to the authenticated owner at the service boundary. Never trust a client-supplied owner ID. Authorization occurs before resolving a user-scoped identifier (CUS10, SR20–SR21).
2. Original bytes are immutable; normalized records, computed metrics, model assessments, user-confirmed context, and failures remain distinct. Every derived item carries source or input references and producing versions (CUS02–03, CUS08; SR03, SR05, SR07, SR16–17, SR28–29).
3. Deterministic ingest, transformation and eligibility do not call a model. Eligibility completes before creating an execution request; ineligible selections expose unmet rules and produce zero provider calls (CUS03, CUS05; SR05–07, SR10–11).
4. The skill contract contains no provider-specific transport or secret. One explicitly selected customer-owned connection/model is pinned to each run. No fallback to another provider, model or platform-owned analysis credential (CUS04, CUS06–07; SR09, SR12–15, SR30).
5. A run is not successful until the response passes the approved versioned output schema and all evidence references resolve to the run snapshot. Invalid or partial model responses are sanitized failure artifacts, not assessments (CUS07–08; SR15–17, SR29).
6. Read views and API retrieval use saved values only; they make no inference calls. Dashboard and API derive from the same authorized resource contract (CUS09; SR18–19, SR31).
7. P1 recommendation/routine/feedback behavior, paid mechanisms, and source-to-skill automation are excluded (CUS11–13 and deferred roadmap stages).

## Required shared schemas before implementation

The following are proposed domain records, independent of technology. Exact JSON Schemas, API schemas and wire details are D02–D04 outputs; implementation must not invent them.

- `Import`: `import_id`, `owner_id` (server derived), `source_digest`, `contract_version`, `status`, `accepted_at`, `warnings[]`, safe rejection/conflict code, parser/profile/preprocessing versions.
- `SourceObject`: owner scope, immutable byte location, digest, byte length, media identification and retention/deletion state.
- `Activity`, `Session`, and optional `Lap` / `Sample` / `Event`: normalized canonical fields and source occurrence/field references. Supported fields are conditional on approved D01 evidence.
- `Snapshot`: immutable `snapshot_id`, canonical scope, digest, included record IDs, exclusion counts/reasons, preprocessing version and creation time.
- `SkillDefinition`: immutable ID/version, declared inputs, deterministic applicability and quality rules, method description, output schema, evaluation suite/version; no provider/secret fields.
- `Eligibility`: snapshot/skill IDs and versions, rule version, boolean, unmet requirements and warnings. It is computed deterministically and retained for the execution attempt.
- `Connection`: owner-scoped connection ID, provider/model capability reference and secret-store reference. Secret bytes are never returned to clients.
- `Run`: groups one user-confirmed combination of one or more eligible skills against one immutable snapshot and one explicitly selected model connection. It records owner, creation time and aggregate lifecycle state.
- `SelectedSkillExecution`: one child per selected skill version, with its own eligibility result, run state, attempts, validated result or sanitized failure. The relationship supports a user-selected skill combination without embedding a skill list inside one opaque prompt/result.
- `Attempt`: one adapter dispatch for a `SelectedSkillExecution`, with timestamps, normalized provider outcome, safe error and usage when supported. Retry is a separate attempt only under an approved retry rule and never changes the selected provider/model.
- `AssessmentResult`: at most one validated result per selected skill execution; findings belong to that result. A failed execution has a distinct failure artifact and no assessment result.
- `Assessment` / `Finding`: separate from observations and metrics; each finding carries classification, typed value/unit and one or more resolvable evidence refs.
- `Evidence`: snapshot-local reference to source record, computed metric with method and inputs, or approved external basis. API never exposes a broader source object by following a reference.

## Definition of Done for each implementation unit

1. Its dependent decisions are founder-approved and recorded; requirement records are valid and synchronized.
2. Inputs, outputs, schema versions, state transitions, error codes and access checks match the approved contract.
3. Unit, boundary, negative, contract and recovery tests for the unit exist and pass against the stated synthetic/disposable fixtures; tests identify execution environment and commit.
4. Provenance, isolation and secret exclusion are observable through test or inspection evidence.
5. The implementer records files, commit, actual checks, outcomes, defects and blocked cases; registry status remains Implemented until candidate-specific verification exists.
6. Independent Reviewer and Quality Manager sign off their assigned review scope before Done; acceptance/release remain separate.

## Proposed combined-run lifecycle requiring WP04 contract approval

The product direction permits users to select skill combinations. Proposed model: reject creation of a run if any selected skill is not eligible; do not silently drop ineligible members. Once accepted, create one child execution per selected skill, all pinned to the same snapshot and connection/model. Child failures remain isolated and visible. The aggregate run remains `running` while any child is nonterminal; `succeeded` when all children succeed; `failed` when none succeeds and at least one fails; `partial` when at least one succeeds and at least one fails. This adds an aggregate `partial` state beyond the current SR14 examples and therefore requires a synchronized SR/state contract decision before implementation. A retry, when later approved, adds an attempt to the same child execution but cannot overwrite an earlier attempt; re-running the combination creates a new Run. Cancellation and restart recovery remain explicit WP04/D03/D05 gates.

## Proposed transaction boundaries (not yet implementable)

- Rejected input: retain a bounded import-attempt record with reason code and safe diagnostics, but do not retain or expose the rejected bytes as accepted history. Whether a rejected upload's raw bytes are discarded immediately or held briefly for abuse analysis is a retention/security decision (D01/D05 and legal review).
- Accepted input: retain original bytes and normalized records with source references; storage that spans separate blob and metadata stores needs a durable staging/commit marker plus retryable reconciliation. A cross-store transaction cannot be assumed. If reconciliation cannot finish, show an import failure/pending state and do not expose partial accepted history.
- Logical conflict: retain the valid conflicting original and its normalized candidate in quarantined owner scope for explicit user resolution under D01; do not publish it to normal history before resolution.
- The above proposed handling requires explicit idempotency, interruption, orphan cleanup, deletion and audit retention contracts before WP02 can start.
