## Risk-ranked verification approach

Order execution by consequence and dependency: (1) source acceptance, provenance, deterministic preparation and authorization boundaries; (2) skill input/output contracts and deterministic eligibility; (3) selected-model routing, secret handling, and failure states; (4) immutable result history; (5) API/dashboard agreement and rendered workflow; (6) separate athlete and founder validation. Do not use a later level to infer an earlier level passed.

| Level | Purpose and suitable evidence | Limits |
| --- | --- | --- |
| Unit | Parser/normalizer, conversion, limits, canonicalization, metrics, eligibility and output validator over synthetic fixtures; retain command, commit, runtime, fixture manifest/hash, assertion report. | Exercises components; not persistence, auth enforcement, provider behavior, or rendered usability. |
| Contract | Positive and negative FIT mapping manifests, SkillInput/OutputEnvelope and ModelAdapter schemas, API schemas/error contract; retain schema versions, fixture IDs/hashes, validator output and resolved evidence references. | Proposed contracts require D01–D04 approval; schema validity alone does not prove substantive quality. |
| Integration | Disposable isolated storage, two synthetic identities, mocked provider transport, restart/re-read and dashboard/API adapters; retain environment/build identity, setup, sanitized request/response traces, DB assertions, screenshots where applicable. | Mocked routing/failures do not establish live provider compatibility or quality. |
| System | Fixed candidate commit through upload → readiness → eligibility → selected model → persisted result/failure → dashboard/API, plus auth and method-denial checks. | Requires implemented service and a declared deploy/runtime topology (D05); system setup is not product deployment evidence. |
| Rendered UI | Isolated browser and target preflight; record browser/version, OS, viewport, automation path, app/build/commit, actual rendered flows and screenshots/video with synthetic users/data. | API or source tests are not rendered UI evidence. No browser/target is available in this design task. |
| Live-model integration | Explicitly selected customer-owned connection using approved disposable credentials and provider-approved test data; record provider/model/API version, capability config, sanitized request IDs, outcome and cost/retention facts. | Never substitute mocks. Requires D03, secure disposable credentials and owner approval; must not use live customer credentials. |
| Athlete validation / founder acceptance | Separate, fixed candidate demonstration with an athlete using approved disposable synthetic data unless an approved nonpersonal fixture exists; capture task completion, interpretation, limitations, unresolved issues and explicit founder decision. | Engineering verification, mocked output, and schema validation cannot establish usefulness or acceptance. |

## Evidence record and execution ownership

Every eventual result should be attached to a fixed candidate and identify: canonical TC ID; CUS/SR; candidate commit; test level; exact command/setup; OS/runtime/build and dependency versions; fixture manifest key, provenance and SHA-256; config/preprocessing/skill/schema/adapter versions; selected model identifier where applicable; expected vs actual observation; result; sanitized evidence locator/checksum; defect link and severity if failed; executor and date. Preserve prior candidate reports; append a new candidate result rather than rewriting historical evidence. Keep secrets, personal telemetry, raw provider payloads, and runtime data out of public artifacts. Controlled nonpublic evidence must have an access-controlled location and review note.

WP01 contract/source evidence is a prerequisite and belongs to TK01/TK02 reviewers. Product unit, contract, and integration evidence belongs to the implementation owners for TK03–TK06. WP06 verification owner runs the fixed-candidate system suite and records reproducible defects; UI acceptance records the actual browser/version, viewport, isolated target and automation path. Athlete validation and founder acceptance remain separate gates and cannot be delegated to a passing test result. If a required environment, approved fixture, provider, browser, or stakeholder is unavailable, record the affected TC as blocked/not run with the blocker; never lower the test level or substitute a mock and report equivalent evidence.

## Coverage gaps and blockers

1. **Approval blockers:** D01 official FIT support matrix, limits, identity/conflict policy and fixture rights; D02 skills, evaluation rubric, trend/coverage thresholds; D03 provider capability, credential boundary, retention and error/retry mapping; D04 dashboard/API semantics, auth, pagination and evidence representation; D05 runtime topology and owners. Freeze exact expected values only after these decisions. WP02–WP06 cannot claim contract conformance before their relevant approvals.
2. **Official data evidence:** the WP01 package records failed official-source retrieval. TC19 has no source-backed mapping yet; do not create binary fixture oracles by guessing protocol details. Source conformance claims are blocked until official evidence and lawful fixture provenance are supplied and reviewed.
3. **Model evidence:** TC08/TC10 mocked tests demonstrate routing/failure mechanics only. TC06 substantive quality on every supported connection and TC15 live journey need separately approved disposable customer-owned access and provider-compatible schemas. No live-model test is authorized or run by this design assignment.
4. **Browser/system evidence:** no product target, isolated browser or rendered UI is verified here. TC12, TC14 UI races and TC15 require browser/target preflight and recorded rendered flow; API assertions cannot close these gaps.
5. **Perspective gaps:** current cases do not fully specify legal/privacy basis and source/license review beyond fixture provenance; retention/deletion/export and backup/restore/availability; operational monitoring, audit completeness, rate limiting/resource-exhaustion recovery, migration/rollback and incident response; accessibility (keyboard-only operation, focus order, labels, contrast, zoom/reflow, screen-reader names/errors); and localization/time-zone comprehension. Add explicit SR/verification coverage through the normal change process before claiming full perspective coverage. Do not silently expand/relabel existing TC IDs.
6. **Recovery and boundary cases:** implementation-level recovery oracles are still needed for interrupted uploads, partial batch commit/rollback, disk/database failure, interrupted model request, restart during pending run, corrupted stored originals/evidence, backup restore, token revocation, provider rate limits, and cleanup of disposable users/secrets. Assign to appropriate owners and requirements before release; TC10's mock error set alone does not cover operational recovery.
7. **Evidence retention:** exact retention duration, deletion semantics, evidence-link expiry, API pagination limits, secret rotation, and retention of sanitized failure evidence remain unapproved. Evidence must not persist sensitive response bodies merely to improve test diagnostics.
