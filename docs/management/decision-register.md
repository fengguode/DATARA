The [Code of Conduct](../../CODE_OF_CONDUCT.md#agent-identity-labels) records the canonical form, the model-evidence ladder, the applicable and non-applicable surfaces, and the limit that the label is a display string rather than a machine key. This supplements the founder-approved attribution agreement in [issue #23](https://github.com/fengguode/DATARA/issues/23); it does not replace it. The clauses of that agreement remain in force, including the Project **Agent** field as an ownership value, GitHub repository labels as `Role — Name`, accurate Git author and committer identities, and the absence of agent publishing authority.

Scope limits agreed with the founder on the same date: the Project **Agent** field and GitHub repository labels keep the short `Role — Name` form because they record ownership rather than a run's model, and a single-select field cannot hold one value per role, model, and harness combination. Historical commits, comments, dated review records, and registry owner fields are preserved as written. The ten tracked Codex role definitions in `.codex/agents/*.toml` were updated in the same change so Codex runs emit a conforming label.

An OpenCode role-definition harness exists as a trial artifact for the parallel Codex/OpenCode comparison. It is **not part of this baseline and is not tracked by this change**. Until it is tracked under its own review, no tracked document treats it as the configuration source of record, and no compliance is claimed for it. The `Model used:` value published from an OpenCode run is therefore self-reported by that run and carries no baseline provenance.

A label records a persona and its runtime only. It does not prove participation, native role activation, independent review, acceptance, or release, and it creates no GitHub account or independent runtime identity. This decision changes no product contract, requirement, priority, or evidence state.

## G0 replacement for Milestone A (1 October 2026)

The founder authorised a G0 replacement under the Code of Conduct rule that coding requires G0 "or its approved replacement", which had never been pulled. The round table's Architect, Product Manager, and Controller reached the same conclusion independently: the binding constraint is **decision closure rather than decision absence**. The operative contracts largely exist in the dated decision baseline, while approximately 95 individually gated subtasks stand between the project and its first line of code, and the TK02 gate cannot close as scheduled because all eight of its children are written to forbid selecting a behaviour while G0 requires approved contracts.

**Authorised scope — Milestone A.** Source acceptance per D01; immutable original storage with SHA-256; exact-duplicate idempotence and logical-tuple quarantine; deterministic normalisation of the four P0 required inputs with no imputation; a deterministic, pure eligibility function that explains unmet requirements and makes no model call; saved history with a read surface; two-identity isolation; and a read-only API returning the same saved values as the page. Milestone A is authorised to proceed to implementation **without G0**.

**Not waived, and no criterion waived by silence.** G0 is defined with six criteria at `docs/management/p0-implementation-plan.md:34-39`. Each is dispositioned individually:

| # | G0 criterion | Status for Milestone A |
| --- | --- | --- |
| 1 | D01 protocol/profile/decoder evidence, supported matrix, resource limits, conflict policy | Partially substituted. **Still unmet: fixture origin, terms, hashes, intended oracles, rights and unknowns.** Accepted risk |
| 2 | D02 shortlist, eligibility/coverage/trend rules, rubric and thresholds | Partially substituted. **Still unmet: evaluation rubric anchors and live evaluation.** Accepted risk |
| 3 | D03 capability, credential, retention, safe errors | **Not waived.** Not needed for Milestone A, which makes no provider call |
| 4 | D04 dashboard outcome, read-only resource/evidence/pagination/access behaviour | Partially substituted. **Still unmet: exact schemas, pagination, accessibility scope.** Accepted risk |
| 5 | D05 stack and topology, platform/browser/accessibility scope, operational ownership, pinned install/run/test commands | Stack and topology substituted. **Still unmet: operational ownership.** Pinned install/run/test commands are **added to Milestone A scope** and must exist before any Milestone A result is offered as evidence |
| 6 | TK02 completion and a first-coding-assignment specification | Substituted **for Milestone A only**. A bounded assignment must still name concrete paths, the fixture, command and environment identity, acceptance cases, owner, and an independent reviewer. **TK02 itself does not close** |

G0 continues to gate, unchanged: provider and model integration, skill execution, the TC15 athlete journey, and the release gate. Also unchanged and not tradeable: user isolation, immutable originals, determinism, provenance on every number, the no-silent-fallback rule, rights and privacy handling, and the release gate.

The founder accepts that Milestone A proceeds as **accepted risk** while D01 fixture provenance and rights, D02 evaluation anchors, D04 exact schemas and accessibility scope, and D05 operational ownership remain unmet. That acceptance is bounded to Milestone A, is not a precedent for widening the replacement, and no G0 criterion is treated as satisfied by silence.

**Binding architectural condition, stated by meaning rather than by name.** Milestone A persists only `Import`, `SourceObject`, `Activity`/`Session`, and `Snapshot` — **and none of them stores a skill-against-model outcome.** A computed value may be persisted only as a **deterministic observation about a snapshot** — reproducible from stored inputs by a versioned method, naming no model and carrying no skill version.

**Three supporting records are in scope and are not findings.** `Eligibility` (`implementation-contracts.md:36`) is required by the authorised scope's deterministic eligibility function, which must explain unmet requirements; it is retained, not thrown away, and it records a rule version and a boolean, not a model outcome. `Evidence` (`:43`) is required by the non-tradeable "provenance on every number" and is snapshot-local, so with no Milestone A run it can only ever resolve to a source record or a computed metric. The quarantined conflicting original and its normalised candidate are required by the scope's "logical-tuple quarantine" and by `:62`; quarantine is a disposition state on the source chain, not a finding. Deterministic reason, warning, rule-version and classification fields on any of these records are in scope.

**The exclusion is semantic, and naming a prohibited entity differently does not satisfy it.** No entity whose meaning is *the outcome of executing a skill against a model* may be persisted, under this name or any other. That excludes, by meaning, anything carrying a skill result, a model verdict, a generated recommendation, or a classification of an activity's meaning rather than of its data. The SR16 rationale is confined to that meaning: SR16 requires every stored **assessment** to carry skill version, model identifier and execution time, so a run-less record that claimed to be an assessment would force a provenance-column migration on exactly the rows the absence exists to protect. A deterministic **data-quality** observation — an out-of-range field, a decode warning, a quarantined conflict — is *not* that meaning, is reproducible from stored inputs by a versioned method, names no model, and is therefore permitted. Naming it `QualityFinding` is neither required nor forbidden by this condition; what governs is the meaning, not the word. No mutable "latest result" or current-value pointer may exist on any entity.

`Metric` is retained in the chain as a deterministic observation, with a stated limit: the contracts **reference** computed metrics (`:8`, `:21`, and `Evidence` at `:43` as *computed metric with method and inputs*) but define **no schema of their own**. That field contract is a D02/WP02 output and is not yet authored; Milestone A must not invent it, and any metric persisted before that contract exists is provisional.

**Correction to the reasoning previously recorded here.** This entry previously stated that SR14 specifies a single run, and that persistence would collide with *selected* deletion-ledger and reapply-on-restore semantics. Both were inaccurate and are withdrawn. SR14 already requires recording *selected skill versions* in the plural; SR17 already requires a re-run to create a new assessment without overwriting the previous; and `implementation-contracts.md:38` already models a combination of *one or more* eligible skills. The real, narrower reason is that SR14's `pending`/`running`/`succeeded`/`failed` states do not yet admit the aggregate `partial` outcome a multi-skill combination needs, which `:56` records as requiring a synchronized SR/state contract decision before implementation — persisting the entity now would fix a shape that decision may still change. And the deletion-ledger and reapply-on-restore semantics are **not selected**: `implementation-contracts.md:58-63` heads that section *Proposed transaction boundaries (**not yet implementable**)* and requires deletion and audit-retention contracts before WP02 can start, while `source-evidence/duplicate-conflict-options.md:37,48` records that deletion and backup behaviour must still be settled. Omitting the execution entities is what keeps that undecided contract from being foreclosed by schema.

**Language discipline.** Milestone A is **not** the P0 first milestone, **not** a first usable release, and **not** an MVP. It is a trust outcome. Nothing produced under it may be described as Done, Verified, Accepted, or released. The first customer-recognisable utility outcome remains the first live baseline-skill run on the athlete's own model, retrievable unchanged from both dashboard and API.

**Evidence basis, and its limits.** A spike ran the pinned `garmin-fit-sdk` **21.217.0** (tag `production/release/21.217.0-0-g248b1c46`) against one real founder-supplied Garmin Connect export. The decode completed with CRC verification enabled, yielding 40 message definitions, 3,880 record messages, and **zero** compressed-timestamp definitions. The file is private and local, is excluded from the repository, and **no hash of it is recorded here or published**, pending the separate founder privacy decision. The spike is an observation, not TC01 or TC19 evidence, and not conformance evidence: a single successful decode proves neither mapping correctness nor coverage of the supported population.

**The compressed-timestamp blocker remains open and is not resolved by that spike.** `docs/p0-design/fit-support-matrix.md:58` records that the pinned decoder explicitly rejects compressed timestamp records, and the SDK source confirms the path is unreachable in 21.217.0. The spike shows the founder's current single-activity export does not exercise that path; it does not show that no file in the supported population does. The D01 engine and coverage decision therefore remains open, and D01 fixture provenance, terms, hashes, intended oracles, and rights remain unmet, as recorded above.

Per the dated baseline, local import, preparation, and saved-history viewing require no provider call, so Milestone A is immune to the open provider-reachability question.

This decision authorises one bounded implementation increment to begin. It approves no product candidate, accepts no requirement, authorises no release, and changes no CUS, SR, priority, contract, or evidence state. ## 3 October 2026 — five architecture decisions closing contracts TK11 and TK15 could not implement

Author: System Architect — Feng Guo_space-bunny-free-max_OpenCode (AI agent), session worktree at `opencode/arch-block-decisions`, base `8acccbf`. Issued under the founder's parallel working mode of 2 October 2026. **Architecture decisions only. No requirement is marked Done, Verified, Accepted or released, no priority changes, no CUS/SR/FEAT state changes, and no registry was edited.** Detailed text: [`fit-support-matrix.md`](../p0-design/fit-support-matrix.md) §12, [`duplicate-conflict-options.md`](source-evidence/duplicate-conflict-options.md) §13–§15, [`decision-proposals.md`](../p0-design/decision-proposals.md) "Routed requirement changes", and the new [`fit-profile-enum-derivation.md`](source-evidence/fit-profile-enum-derivation.md).

**D-A1 — the sub-sport allowlist is frozen; indoor/outdoor is a positive-evidence label only.** The pinned `profile.py` bytes were re-verified by SHA-256 against MAP01 on 3 October 2026 (`cfc2737…865c`, 967399 bytes, match) before any value was read, and the enums were parsed, never imported. The 112 `sub_sport` values partition exhaustively: **9** assigned to `sport` 1 `running`, **19** to `sport` 2 `cycling`, one shared (`0 generic`), **84** assigned to neither, and `254`. The previous matrix had approved only 6 cycling values and had **silently dropped 11 cycling-tagged sub-sports** the publisher assigns to cycling, including `track_cycling` 13, `bmx` 29, `commuting` 48 and `e_bike_enduro` 127. Classification is `indoor` only on a publisher-written `indoor` token or a fixed indoor apparatus (`treadmill`), `outdoor` only on a way or landform that exists only outdoors (`street`, `trail`, `road`, `mountain`), and `null` otherwise. `track` 4 and `gravel_cycling` 46 are **corrected from `outdoor` to `null`**: both name a surface, and both surfaces exist indoors. The rule is deliberately asymmetric because the reverse rule is demonstrably false on the pinned data — it would label `spin` 5 `outdoor`, and a false `outdoor` is a false statement about the athlete's activity, whereas a `null` is only the absence of a claim. The cost is stated, not hidden: gravel, cyclocross, track, commute and other discipline-named activities import normally with a `null` label. **No inference from GPS absence** is permitted or possible; the profile declares no indoor/outdoor field on `sub_sport` or on `session` 18, which is why the name is the only evidence and the rule must be strict.

**D-A2 — `254 all` is rejected for both `sport` and `sub_sport`, with unequal and separately labelled evidence.** For `sport` the goals-only reading is **verified** from the publisher's own comment at `profile.py:27269` ("All is for goals only to include all sports"). For `sub_sport` the entry at `profile.py:27446` is bare and carries no comment, so the goals-only reading is **inferred by analogy** and is labelled as such; it stands independently on the profile's own `file` enum, which gives `11 goals` its own file category. `sport = 254` was already rejected by the `{1, 2}` whitelist and gains a dedicated explanation, `SPORT_ALL_GOALS_ONLY`, with no accept/reject behaviour change. `sub_sport = 254` is rejected with `SUBSPORT_ALL_GOALS_ONLY` — the single exception to "an unapproved sub-sport never rejects", justified because `all` is not an unclassified variant but a declaration of a multi-sport aggregate, which is the same scope contradiction as the already-rejected `activity.type = auto_multi_sport`.

**D-A3 — an unknown, unassigned or cross-sport sub-sport is accepted with disclosure and never rejected.** `sub_sport` is optional; `sport` is the required, profile-authoritative field. Rejecting a whole file over an optional taxonomy edge case would shrink the supported population below what D01 selected, in D01's own name. Four distinct causes, four stable codes, all resolving to `null` with the raw value retained: `SUBSPORT_ABSENT`, `SUBSPORT_INVALID`, `SUBSPORT_SPORT_MISMATCH`, `SUBSPORT_UNMAPPED`. `sub_sport` remains excluded from the conflict tuple, so a re-export that changed only the sub-sport still conflicts.

**D-A4 — the observed `session` count is authoritative; the `activity` message corroborates and never overrides.** Pinned: `activity` is global message 34, field 1 `num_sessions` is `uint16`, and field 2 `type` is `enum/activity` with exactly `0 manual` and `1 auto_multi_sport`. Structure read by walking the message stream is a fact about the file; `num_sessions` is a device-written claim about it, in a field the profile attaches no relation rule to, and it may legitimately be absent. Three outcomes and no fallback: **corroborated** (declared equals observed) accepts silently; **uncorroborated** accepts on the observed count plus a disclosure, and this now has **two** codes because "no `activity` message" and "`activity` present without `num_sessions`" are different facts — the merged implementation discloses neither in the second case, which is a real gap reported to the code owner; **contradicted** (`declared != observed`) is a **rejection**, `SESSION_COUNT_MISMATCH`, never a preference for the friendlier value. The invariant is `declared == observed`, not `declared == 1`; the current code's `!= 1` test is equivalent only because the observed count is already forced to 1.

**D-A5 — `P1` as written was unimplementable, and the schema was right.** P1 required "a new `Import` row records the attempt and the reference". Verified three ways against the merged source: `datara/dedup.py:756-777` returns without creating an `Import`; `datara/models.py:216-219` makes a second row for the same `(owner, source_digest, contract_version)` impossible; and the `Import` model has **no column for a reference at all**. The decision is that **one `Import` row per digest is the intent and P1's wording was wrong**, on three internal pieces of evidence: P1 itself asserts "Idempotent", which a per-attempt row would falsify; **P6 depends on it**, because a per-attempt row left by a rejected attempt would make P1 match it and render P6 unreachable; and the shipped unique constraint already encodes the one-row reading. **The P1 cell is corrected in place; the `Import` docstring and an invariant test are routed to the code owner.** The reference needs no new column — under one row per digest it is derivable from the digest itself, and `describe_reference` already renders it. Five per-file dispositions and three `Import` statuses are two different vocabularies at two different levels, and a duplicate is an outcome, not a status. **The constraint must not be relaxed**; a per-submission audit trail would be a new `SubmissionAttempt` entity, and `SR32` needs no stored per-submission record. With P1 corrected, TK15 can claim conformance for the duplicate path once the invariant test exists — not before.

**Routed, not decided here.** The corrected `SR32` text covering all five dispositions, the `SR32`/`SR33` boundary and mapping, and the `elapsed_duration_seconds` → `_ms` contract version bump with its digest-migration options are in [`decision-proposals.md`](../p0-design/decision-proposals.md) R1–R4, with exact JSON, Markdown and line-level change locations. **The registry edit is not mine** and none of the four registry/mirror files was touched. The `_ms` change is a **version bump plus digest migration, not a rename**: the key is inside the payload whose SHA-256 *is* the `normalization_digest`, so a bare rename would silently re-base every stored digest, which `SR05` forbids; `Activity` already carries `contract_version`, so digests are self-describing and old and new can coexist, and version-scoping is recommended over recomputation. Two `#325` items are resolved: the **wellness mapping is confirmed in principle but incomplete** — 21.217.0 has no `wellness` file enum and monitoring data sits under five categories while only three are mapped — and the **chained-file flag position decision is confirmed unchanged**, because the protocol prose was never captured, so the flag must not be asserted from memory and the trailing-bytes rule stands as the derived mechanism.

**Divergences found and reported to their owners, not fixed.** `datara/**` is not mine to edit. (a) The matrix has always specified separate codes for a multi-`session` file and a chained layout; the implementation collapses multisession counting and the `auto_multi_sport` assertion into one reason. (b) `monitoring_a` and `monitoring_b` fall through to a generic file-type reason instead of the named wellness exclusion. (c) The `activity`-present-but-`num_sessions`-absent case produces no disclosure. (d) The `Import` docstring and the missing P1 invariant test. All four are recorded above with file and line.

**Unchanged and still open.** The compressed-timestamp engine and coverage decision, so **coverage of the supported population remains unproven** and freezing an allowlist says only what the profile can express. Date-time bounds as protocol rules, header CRC exception rules, the chained-flag position, fixture oracles and their rights, SDK licence terms, and package-byte verification. `goals` (11) and `activity_summary` (20) file-type reasons. The R4 digest-migration option is a product-data decision for the founder via the Primary Coordinator. `OQ-1`–`OQ-5` in `duplicate-conflict-options.md` §11 are untouched.

**Evidence basis and its limits.** All profile claims are **verified** by SHA-256-matched parse of the pinned bytes at `8acccbf`, with a source line recorded for every enum value; engineering judgements are labelled **inferred** at the point of use; implementation claims are **verified by reading the merged source**. No SDK was imported or executed for these decisions, no fixture or sample was acquired, no terms were accepted, and no rights conclusion is drawn. `demo_file/` was not read, copied, hashed, stat-ed or listed.
