## Conflict policy — architecture recommendation (2 October 2026, TK14)

The 1 October WP01 framing asked the founder to choose between "exact logical tuple + manual resolution", "tolerance-based key" and "no logical duplicate check". Those are not three answers to one question: digest-only detection answers *is this the same file?*, tuple quarantine answers *might these be the same activity?*, and explicit resolution answers *who decides?*. Presenting them as alternatives invited a choice that could only have been wrong.

**Recommendation: hybrid precedence — digest-only idempotence, then logical-tuple quarantine, then explicit owner resolution — with an explicit precedence rule for every submission.** Digest-only alone cannot surface a conflict at all; quarantine alone is a dead end with no exit; resolution alone never fires. Rejecting tolerance matching is not only a rule but an engineering judgement: an approximate match that is wrong destroys information, and unlike every other failure mode here it cannot be undone by an explicit user action.

This recommends the structure D01 already selected; it does not reopen a founder decision. What it adds is the precedence order, the concurrency and lost-response rules, and the athlete-facing wording rules that TK15 and TK16 would otherwise have to invent. Two items still need a founder decision rather than an architectural one: whether a "retain both" resolution suppresses future quarantines for that tuple (**recommended: no**), and the retention/deletion interaction with supersession lineage, which remains unselected.

**Two requirement gaps this exposes, which the architect cannot close.** `SR32` admits only an accepted/rejected disposition, but duplicate references and quarantines are neither; collapsing them would mislead the athlete. `SR33` covers the history view but not the per-file upload outcome. Both are routed to the Primary Coordinator as synchronized registry changes.

Full comparison, precedence table, invariants and presentation contract: [duplicate and conflict policy comparison](../management/source-evidence/duplicate-conflict-options.md). No test, acceptance or release state changes here.

## D03 cost evidence and pause/resume controls

The Controller review found no DATARA usage, billing, runtime or product telemetry. Actual provider spend and DATARA infrastructure cost are therefore **unmeasured**. Do not make an estimate until each model attempt can retain sanitized usage units, provider/model/API version, request ID, currency and price schedule date. A scenario estimate should state assumptions for run frequency, selected skill count, input/output size, retries/failed attempts, provider/model and dated rates, with low/base/high bounds. Customer-owned provider charges and DATARA infrastructure/operations costs must be reported separately.

Before each live-model call, pause if the provider/model/API version, data class and fixture provenance, customer credential owner authorization, bounded request size, approved usage ceiling, or evidence fields are missing. Pause on unexpected retention terms, authentication behavior, fallback/retry ambiguity, secret exposure, or a ceiling breach. The operator stops calls; Controller monitors usage evidence; the security/operations owner handles data/secret events; founder approves provider/scope changes. Resume only after a named owner records corrected configuration/limit/authorization; preserve prior blocked/failed results and rerun only affected cases on the fixed candidate. This is a proposed gate, not a change to any token or spending budget.
