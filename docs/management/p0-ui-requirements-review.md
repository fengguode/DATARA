## Purpose and status

This review maps the athlete-facing P0 journey across CUS01–CUS10 to design concerns, candidate atomic UI requirements, acceptance suggestions, and implementation work packages. Existing CUS and SR statements remain canonical in `product-requirements.md` and `system-requirements.md`. Every `UI-SR` below is a **proposed derived obligation**, not a new approved SR, and every `UI-F`/`UI-T`/`UI-ST` is a proposed planning identifier, not a GitHub item or commitment.

The UI is a presentation and control surface for approved deterministic contracts. It must distinguish source observations, calculated values, model assessments, run failures, and limitations. Viewing saved history does not call a model. Proposed visual copy, status presentation, and keyboard/screen-reader details do not set legal/privacy controls, performance targets, supported screen sizes, or data thresholds. The Architect should decide whether the candidate SRs merit canonical SR records and trace them to CUS; the founder decides any material customer outcome or product-scope change.

## Journey and state coverage

The flow is: upload supported files → inspect disposition and retained activity history → choose a data scope and inspect deterministic readiness/quality → inspect eligible skills → explicitly choose a supported skill and customer model → submit a manual run → inspect pending/running/succeeded/failed outcome → revisit saved evidence and history → retrieve the same saved values through the authorized read-only API. Every step is scoped to the authenticated user.

| Flow | Existing trace | User-visible states and recovery concern | Planned evidence (not run) |
|---|---|---|---|
| Upload and file disposition | CUS01; SR01–SR02, SR27 | Idle, uploading/processing, accepted, rejected with stable reason, and conflict where supported by approved contract. Distinguish file-level failure from accepted history; never imply unsupported files were imported. Keep reasons available as text and identify the affected file. | TC01, TC19; upload portion of TC15 |
| Persistent activity history | CUS02; SR03–SR04 | First-use empty history, loading, populated history, duplicate re-upload reference, visible unresolved conflict, and retrieval failure. Do not make duplicate upload look like another activity or imply a conflict was silently resolved. | TC02–TC03; TC11; history portion of TC15 |
| Readiness and data quality | CUS03; SR05–SR07, SR28 | No accepted data, preparing/loading, ready, partial optional-field warnings, blocking input/quality gap, and service failure. Keep measured/source values distinct from calculated metrics; expose the relevant period and scope. | TC04–TC05, TC20; readiness portion of TC15 |
| Skill library and eligibility | CUS04–CUS05; SR08–SR11, SR29 | Approved skills available, no library entries, loading, eligible, ineligible with unmet requirements, and unavailable evaluation/contract data. Ineligible skills cannot be submitted; missing inputs are text, not color alone. Only the approved baseline appears. | TC06–TC07, TC20; selection portion of TC15 |
| Customer connection and model choice | CUS06; SR12–SR13, SR30 | No configured supported connection, explicit selected connection/model, validating or unavailable connection, authentication failure, and safe recovery. Never display a secret, silently switch connection, or imply that unsupported connections can run. | TC08–TC09, TC20; selection/run portion of TC15 |
| Manual run | CUS07; SR14–SR15, SR30 | Pending, running, succeeded with validated result, failed/invalid result, timeout, authentication/provider error. Show selected scope, skill version, and model before the user starts; only a validated success is presented as an assessment. A failed run must remain visibly failed. | TC10, TC20; run/failure portion of TC15 |
| Saved lineage and result history | CUS08; SR16–SR17, SR29 | No prior runs, loading, immutable prior run detail, evidence available/unresolvable, prior failure, and a new run beside earlier history. Clearly label snapshot, preprocessing, skill/model versions, run time, evidence, and limitations when supplied by the approved record. Viewing a run does not regenerate it. | TC11–TC12, TC20; revisit portion of TC15 |
| Dashboard and read-only retrieval | CUS09; SR18–SR19, SR31 | Dashboard loading/empty/saved-data states, saved failures, unavailable evidence, API unavailable/authentication denied, and read-only method rejection as a safe error. Dashboard values should derive from the same approved versioned contracts as API values. | TC12–TC13, TC20; retrieval portion of TC15 |
| User isolation | CUS10; SR20–SR21 | Unauthenticated, authorized, unauthorized/undisclosable resource, expired/changed identity, and denied action. Never render another user's resource or reveal its existence through substituted identifiers. Clear or re-scope identity-bound UI state on identity change. | TC09, TC14; two-user journey within TC15 where applicable |

Across each interactive view, design and later rendered acceptance should cover applicable loading, empty, success, failure, and permission states. A state that cannot occur for a view may be marked not applicable with its reason. API checks alone do not establish rendered usability. Responsive viewports and screen-reader/browser combinations must be declared by the implementation/test plan before acceptance; this review sets no unsupported target list.

## Candidate atomic UI-derived SRs and acceptance suggestions

These statements are suggestions for Architect review and registry traceability. IDs are local placeholders only; they must not be treated as canonical SR identifiers.

| Proposal | Parent CUS / existing SR | Candidate obligation | Concrete acceptance suggestion |
|---|---|---|---|
| UI-SR01 | CUS01; SR01–SR02, SR27 | Each upload disposition shall be presented with a textual status and the applicable approved reason, associated with the submitted file. | Exercise each approved accepted/rejected/conflict fixture; a user can identify the file and outcome without relying on color or icon alone. Unsupported variants remain rejected under the approved source matrix. |
| UI-SR02 | CUS02; SR03–SR04 | The history view shall distinguish persisted activities, exact duplicate imports, and unresolved conflicts according to the approved persistence contract. | Re-upload identical bytes and submit an approved conflict fixture; history does not count the exact duplicate as a new activity and does not imply a conflict was merged or overwritten. |
| UI-SR03 | CUS03; SR05–SR07, SR28 | Readiness presentation shall label source observations, computed metrics, quality warnings, and selected data scope according to their contract provenance. | For a known fixture, compare displayed scope and labels with the prepared records; optional missing data is shown as unavailable/unknown rather than invented as zero. |
| UI-SR04 | CUS04–CUS05; SR08–SR11, SR29 | Skill selection shall expose approved skill applicability and deterministic eligibility; an ineligible skill shall not be submitted for execution and its unmet requirements shall be identifiable. | Remove a mandatory input; verify the affected skill is blocked before any run request and its specific unmet rule is displayed. Verify an eligible skill remains selectable. |
| UI-SR05 | CUS06; SR12–SR13, SR30 | Before a run, the interface shall identify the explicitly selected supported customer connection and model and shall not expose credential material or imply an automatic fallback. | Simulate unavailable/rejected selected access; the displayed selection remains explicit, the run is not routed to another connection, and UI/network-visible output contains no secret. |
| UI-SR06 | CUS07; SR14–SR15, SR30 | Each submitted run shall expose its actual pending/running/succeeded/failed state; only a validated successful response shall be presented as a successful assessment. | Exercise valid response, malformed response, authentication failure, and timeout. Each visible state matches persisted run outcome; failures do not appear in successful findings. |
| UI-SR07 | CUS08; SR16–SR17, SR29 | A saved result view shall show the lineage fields and evidence/limitations supplied by the result contract, and a rerun shall appear as a separate history item. | Save a run, reload history, and rerun the same scope; the prior record remains available with its own versions/evidence, and viewing it causes no inference request. |
| UI-SR08 | CUS09; SR18–SR19, SR31 | Dashboard saved values shall be sourced from the approved versioned output contract, and the read-only API shall be represented as retrieval only. | For a fixed candidate fixture, compare visible saved values and identifiers with authorized API responses; rejected mutation methods yield the approved read-only error. |
| UI-SR09 | CUS10; SR20–SR21 | UI retrieval and actions shall remain bound to the authenticated user and shall render unauthorized or undisclosable resources without leaking another user's data or resource existence. | With two disposable accounts, substitute activity/run identifiers and change identity during an open history view; no other user's values appear and requests are denied per approved authorization behavior. |
| UI-SR10 | CUS01–CUS10 as applicable; cross-cutting accessibility obligation for Architect assessment | Every P0 interactive flow shall be operable by keyboard, expose a meaningful semantic name/role/value, associate errors with affected controls, and announce asynchronous status changes to assistive technology. | In supported browser/assistive-technology combinations selected by the test plan, complete upload disposition, skill/model selection, run status, result history, and denial/error recovery using keyboard and screen-reader output. Confirm focus remains perceivable after state changes. |
| UI-SR11 | CUS01–CUS10 as applicable; cross-cutting accessibility obligation for Architect assessment | Status and eligibility shall not depend on color alone; responsive presentation shall preserve labels, actions, and content relationships at the supported viewport sizes approved for the product. | Inspect approved status variants without color cues and exercise the declared viewport set; confirm no action/status becomes unavailable or obscured. The viewport set and any formal conformance target remain to be selected. |

UI-SR10/11 are not a claim that the present SR baseline includes complete accessibility coverage. Architect should assess applicable accessibility obligations and governing standard/target with the relevant owner before turning them into normative SRs. This review intentionally selects no conformance level, contrast ratio, minimum touch target, viewport dimensions, supported browser matrix, or legal conclusion.

### Dependency and evidence notes

- WP01 decisions/contracts precede UI details that depend on source variants/reasons (D01), skills/eligibility metadata (D02), supported connections and safe credential status (D03), dashboard/API outcome (D04), and implementation environment/viewports (D05). This review does not close any decision.
- WP02 data home/preparation feeds history and readiness; WP03 skills and deterministic eligibility feed selection; WP04 customer connections and manual runs feed saved run records; WP05 dashboard/API consumes those contracts; WP06 validates the integrated P0 journey. Respect these dependencies and do not implement P1 recommendations/routines under these feature proposals.
- Planned case IDs are evidence targets only. Validation-plan status is planning only and no product verification, rendered UI acceptance, live model integration, system verification, or athlete validation has been performed by this review.
- For any rendered acceptance, record candidate full SHA, browser/viewport/assistive-technology setup, test identity and disposable fixture identifiers, actual step-by-step results, failures, and limits. Do not place credentials or personal FIT telemetry in public evidence.
